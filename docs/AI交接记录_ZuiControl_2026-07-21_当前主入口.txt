三、0.21.3 根因、修复与待刷验证

- 当前 V39 仍保留已验收的 P1、UI、AppOpt 三条鸣潮规则、相机、云控删除和 SELinux 状态。本轮不改 P1，不进入 FPS cap。
- 严重时序根因：旧 daemon 只杀 ZuiPP 并等新 PID，GameHelper 的多个 sticky service 会错过重入；新 ZuiPP 的 `PerformanceConnectHelper` 尚未初始化时，provider 会精确 NPE，因此看不到 `notifyPerfStatus 11/17`。0.21.3 改为顺序停 GameHelper -> 停 ZuiPP services -> TERM ZuiPP -> 等新 PID 稳定 3 秒 -> 显式启动 `PerformanceConnect` -> 预热 GameHelper 并稳定 2 秒。设备上临时精确替换 daemon 后，亮屏解锁从桌面启动鸣潮已闭合 `onGameAppStart -> initGameHelper -> notifyPerfStatus 11/17 -> writeSavageMode open=1`。
- GPU 直接根因：旧生成器把用户的 GPU max/min 按表面名字写成 `0_8_-1`，SM8650 TAssistant 实际把后者当成最终上限，所以即使 `quiet-therm=37.8C`、两个 thermal cooling state 都是 0，GPU 仍被锁在 422MHz；中高温配置的下限 500 又会变成 500MHz 上限。可逆实验改为 `8_0_-1` 后，ZuiPP 读到 `GPUMax=8,GPUMin=0`，冷机 `thermal_pwrlevel=0/max_gpuclk=903MHz`，频率可动态波动。0.21.3 已从生成器根修正次序，且通过模板 stamp 迫使升级开机从保留 profile 自动重生 XML，不用用户重新保存。
- 温度并非没有中/高档：当前鸣潮 profile 有默认、42C、48C 三段，P2 取 `back_temp`；系统界面电池 41.6–42C 是另一个 `battery` 传感器。vendor `thermal-engine-v2`/Lenovo performance service/KGSL 主要根据 `quiet-therm`和芯片结温执行最终安全限制；`thermal-engine_gpu_0.conf` 在 quiet 44/46/48/50C 分别限 720/629/500/231MHz，这一安全链会合法覆盖 P2，本轮不修改。`ThermalConfig=0 0 0` 仍包含 user-case 0 的 cpu_0/gpu_0 安全热控，不是关闭温控。
- 后台边界：“通知存在”就表示 App 的轻量前台 service 进程在运行，不是无进程的通知。但已保存 P1 由 system_server 执行，P2 由 XML/ZuiPP/GameHelper/zui_controld 执行，AppOpt 由 init 管理的原生 AppOpt 服务执行；即使强停 ZuiControl 导致快捷通知消失，三者已保存规则仍生效。
