# ZuiControl 当前架构总览

## 当前最终架构

V20.4 Golden source 固定为 `29f23f8d590b88f0d472c12373366a9ef14e8330`。Refresh 由
system_server 按 focused Window 驱动；Uperf scene 由 display-global top-resumed Activity
事件驱动；asoulOpt 是唯一 per-task affinity owner。`zui_controld` 只是
`--oneshot-request` 命令执行器，不是常驻控制面。

## Owner / Authority

- Refresh physical target：system_server focused Window。
- QS/ZuiControl 配置对象：`lastNonTransientScenePackage`，不是 physical owner。
- Uperf scene：display-global `ResumedActivity:`。
- Uperf lifetime：native subreaper + blocking `waitpid`；init 是唯一 restart owner。
- asoulOpt：per-task affinity/context scheduling。
- OEM fence：init-native + `scheduler_active` gate。
- Health：按需 Binder。

## 已淘汰设计

常驻 `zui_controld`、Accessibility/App 作 refresh owner、Uperf FIFO output/EOF lifetime、
5 秒 shell/grep 轮询、`sfanalysis=true`、task-local top-resumed、目录时间推断
candidate。

## 为什么错

它们会引入双重 authority、空值瞬态覆盖、SELinux blocking AVC、假 readiness、
空闲轮询和错包刷写风险。

## 正确做法

只从 Golden manifest 选取基线；修改相关子系统前先读本目录对应文档；
运行产物和工具/文档提交分离。

## 禁止重新引入

`persistent daemon`, `polling owner`, `FIFO lifetime`, `latest directory`,
`app-owned refresh`, `dual restart owner`。

## 必须阅读触发关键词

`architecture`, `owner`, `authority`, `runtime`, `baseline`, `candidate`, `Golden`。
